# ADR-006 — Opt-in nickname retention and explicit session draft recovery

**Status:** Accepted for Sprint 05, issue #12. **Date:** 2026-10-21. Supersedes only the no-storage decisions of ADR-003/004/005 for the narrow records below. Live G0 and all booking/privacy invariants remain unchanged.

## Purpose and consent

MV3 workers stop normally. Re-entering optional nicknames is inconvenient; restoring old booking evidence would be unsafe. Default remains temporary. Only the explicit **Onthoud mijn buddy-bijnamen op dit apparaat** setting enables local retention. Existing memory names never imply consent. Separately, **Bewaar tijdelijk filmplan-concept** is a specific save action, permitted even while nickname retention is off. Neither operation runs automatically, syncs or sends data outside Chrome.

## Records and lifecycle

- `storage.local`, key `seatbuddies.roster.v1`: strict `{version:1, roster:[{id:UUID,nickname}]}`. Maximum twelve unique IDs/normalized, case-insensitively unique nicknames of 1–24 characters. Existing nickname validation rejects links, emails, controls, markup and long numeric identifiers. Key presence with a valid version is the remembered opt-in. No selection, DEMO flag, account, plan, seat, timestamp, context or progress. Explicit demo-roster records cannot be opted in. The same opaque IDs survive worker/browser restart; selection always starts empty and requires a new deliberate choice.
- `storage.session`, key `seatbuddies.draft.v1`: strict `{version:1,createdAt,plan:{movie,cinema,date,time,hall}}`. Film/cinema/time/date are required, hall may be null. Bounded strings; links/email/control characters/long numeric identifiers are rejected in text labels. No names, seats, evidence/status, browser IDs, page times, account or ticket data. Maximum age four hours; future, malformed, oversized and unknown-version records are removed. Only explicit **Herstel concept** returns its fields, which go into the uncommitted form with **Concept, opnieuw controleren**. No PLAN command, checkbox, binding or state promotion is replayed.

Chrome session memory can survive worker suspension, but is not a durable backup: browser restart and extension disable/reload/update clear it. Neither area contains booking/account proof. At worker restart the new coordinator starts with empty plan, selection, independent A/B steps, seats, observations and bindings. The optional restored roster and draft availability do not change that. State polling never fills draft form fields or overwrites unsaved edits.

## Trust boundary and spanning

The only permission addition is **storage**: current manifest is exactly **sidePanel + storage**. Before either key is read/written/deleted, the worker awaits that area's `setAccessLevel({accessLevel:'TRUSTED_CONTEXTS'})`. Failure is visible and disables that retention feature; there is no pretend success or localStorage substitute. Chrome local storage is **not encrypted by default**. Anyone with access to the browser profile or trusted extension code may access it; users should choose non-identifying nicknames. There is no `storage.sync` or backend.

The worker authenticates exact packaged origin/path/frame and validates strict bounded message schemas **before** storage effects. For all popup/panel shared-state operations it additionally looks up the browser-supplied sender document ID through `runtime.getContexts`, verifies document URL/type/frame/incognito/window, and corroborates the window's non-incognito status with `windows.get`. No UI-provided flag or `extension.inIncognitoContext` is trusted: in spanning mode the process flag alone does not prove the originating window. Missing/ambiguous metadata, API failure and incognito UI are rejected before hydration/read/write/reset. The ordinary normal panel may still explicitly bind neutral incognito **metadata** for B; that metadata never enters storage. In an incognito/unknown panel the independent local manual fallback remains available, without shared or retained data.

The popup sees only the limited nickname/control view, never filmplan contents, roles or incognito state. Its draft commands are rejected before storage. The packaged widget receives no remembered nickname/roster through its protocol. Chrome's TRUSTED_CONTEXTS protects against future content scripts; it does **not** sandbox our own packaged fixture from other extension code. Those pages are trusted reviewed code, contain no storage calls and have no remote scripts/connections; a compromised extension bundle is outside this separation guarantee. Production host permissions/content scripts remain absent.

## Concurrency and deletion

A single bounded worker queue (32 requests) serializes hydration, reads, mutations and writes. Hydration finishes before commands can overwrite a saved roster. Generation + monotonic buddy revision gates reject old/replayed opt-in/draft operations and conflicting renames; clients refresh without retrying mutations. A deliberate **disable/delete** from the same worker generation may have an older roster revision: revocation wins over unrelated nickname edits, only deletes retained records and does not replace current names or A/B. Old worker generations still fail closed. The checkbox displays acknowledged consent rather than optimistic success. Existing B-generation/epoch guards and reset barrier also cover requests waiting for browser/storage APIs. Stored data is a strict projection, never a serialized snapshot. A failed write keeps only current memory changes, attempts deletion and reports either temporary fallback or explicitly unconfirmed deletion. It never restores earlier B proof as a rollback.

Disable/**Vergeet opgeslagen buddies** deletes the local key and session draft, retaining current names only in memory. Individual deletion updates the saved projection; removing the last/clearing all deletes the key and turns remembering off. **Wis alle tijdelijke gegevens** and explicit reconnect also remove both saved records and reset client/coordinator data. Expiry and an observed incognito-consent scope change remove the session draft. Uninstall clears local storage. Deletion is acknowledged only after the Chrome promise succeeds; failure instructs the user that deleting the extension clears its storage.

## Migration, rollback and validation

No old persistent schema exists. Unknown versions/corrupt records are deleted rather than migrated or partially trusted; no sensitive quarantine/log copy is made. To roll back, disable remembering/delete the draft before loading an older extension; uninstall is the complete removal path. An older bundle does not understand these keys and must not be described as having deleted them. No destructive migration of user accounts or bookings exists.

Tests cover validated projections, opt-in/default, hydration race/replay, serial writes, deletion/failure, TTL/future values, B independence and no status resurrection. Renderer doubles, real Chrome storage/worker tests and actual normal/incognito popup tests are distinguished in [feasibility](../feasibility.md); human Mac QA follows delivery.
